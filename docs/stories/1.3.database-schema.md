# Story 1.3: Database Schema & Migrations

## Status
Draft

## Story
**As a** developer,  
**I want** a defined database schema for users, vehicles, entries, reminders, and documents with migration scripts,  
**so that** the data model supports all MVP features with referential integrity and can evolve over time through versioned migrations.

## Acceptance Criteria
1. Users table schema defined with email, password_hash, created_at, settings fields
2. Vehicles table schema defined with user_id FK, make, model, year, VIN, license_plate, current_odometer, photo_url, created_at
3. Service_entries, fuel_entries, insurance, documents, reminders table schemas defined per data model
4. Foreign key constraints established to maintain referential integrity (cascade deletes where appropriate)
5. Indexes created on frequently queried fields (user_id, vehicle_id, date fields)
6. Migration script created to initialize schema from scratch
7. Migration script successfully executes against Azure Cosmos DB using SQL API
8. Seed data script created for development/testing with sample records

### Data Model Architecture
**[Source: architecture/04-data-models.md]**

**Core Entities:**
1. **User** - Account information with preferences
   - Fields: id (UUID), email, displayName, createdAt, updatedAt, preferences (distanceUnit, fuelVolumeUnit, currency, locale), syncEnabled, lastSyncAt
   - Relationships: One-to-Many with Vehicle, SyncConflict

2. **Vehicle** - Vehicle being tracked
   - Fields: id (UUID), userId (FK), make, model, year, vin, licensePlate, nickname, currentOdometer, odometerUnit, photoUrl, purchaseDate, purchasePrice, notes, isActive, createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One User, One-to-Many with ServiceEvent, FuelEntry, InsurancePolicy, Document, Reminder

3. **ServiceEvent** - Maintenance and service records
   - Fields: id, vehicleId (FK), date, odometer, serviceType, description, cost, shopName, shopAddress, notes, receiptDocumentIds[], tags[], createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One Vehicle, One-to-Many Document

4. **FuelEntry** - Fuel purchase and economy tracking
   - Fields: id, vehicleId (FK), date, odometer, volume, volumeUnit, costPerUnit, totalCost, isFillUp, stationName, location, fuelGrade, notes, receiptDocumentIds[], createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One Vehicle, One-to-Many Document

5. **InsurancePolicy** - Insurance policy information
   - Fields: id, vehicleId (FK), provider, policyNumber, startDate, endDate, premium, premiumFrequency, coverageType, deductible, notes, documentIds[], createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One Vehicle, One-to-Many Document

6. **Document** - File uploads (receipts, manuals, registration)
   - Fields: id, vehicleId (FK), filename, mimeType, size, category, description, date, localFileKey, cloudBlobUrl, thumbnailLocalKey, thumbnailCloudUrl, linkedEntityType, linkedEntityId, tags[], createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One Vehicle, Optional Many-to-One with ServiceEvent, FuelEntry, InsurancePolicy

7. **Reminder** - Maintenance reminders
   - Fields: id, vehicleId (FK), title, description, reminderType (odometer/date/both), odometerThreshold, dateThreshold, advanceNoticeOdometer, advanceNoticeDays, repeatInterval, status (active/completed/snoozed/dismissed), completedAt, snoozeUntil, linkedServiceType, notes, createdAt, updatedAt, lastSyncedAt, _version
   - Relationships: Many-to-One Vehicle

8. **SyncConflict** - Sync conflict tracking
   - Fields: id, userId (FK), entityType, entityId, localVersion, cloudVersion, localTimestamp, cloudTimestamp, conflictDetectedAt, resolutionStrategy, resolvedAt, resolvedBy, notes
   - Relationships: Many-to-One User

### Azure Cosmos DB Configuration
**[Source: architecture/08-database-schema.md and 10-infrastructure-and-deployment.md]**

**Database Settings:**
- **Database Name:** vehicle-tracker-db
- **API:** SQL API (LINQ-compatible for queries)
- **Partition Strategy:** `/userId` for most containers (ensures data locality and scales with user count)
  - Exception: sync_queue uses `/entityId` to distribute write load
- **Consistency Level:** Session (read-your-writes consistency)
- **Change Feed:** Enabled on all containers except sync-conflicts (for sync processing)
- **TTL Policy:** 30 days on resolved sync-conflicts; 7 days on completed sync-queue entries

**Throughput Configuration:**
- **Development:** 400 RU/s shared across all containers (free tier)
- **Production:** Autoscale 400–4000 RU/s per container (as load increases)

**Indexing Policy:**
```json
{
  "indexingMode": "consistent",
  "automatic": true,
  "includedPaths": [{ "path": "/*" }],
  "excludedPaths": [
    { "path": "/localVersion/*" },
    { "path": "/cloudVersion/*" },
    { "path": "/_etag/?" }
  ]
}
```
Rationale: Exclude version fields from indexing (large objects, not queried). This reduces storage and RU consumption.

### IndexedDB Client-Side Schema
**[Source: architecture/08-database-schema.md]**

**Database Configuration:**
- **Name:** vehicle-tracker
- **Version:** 1
- **Storage Estimate:** 10–15 MB per typical user

**Index Strategy for Client:**
```typescript
db.version(1).stores({
  users: 'id, email, lastSyncAt',
  vehicles: 'id, userId, isActive, currentOdometer, [userId+isActive]',
  serviceEvents: 'id, vehicleId, date, odometer, serviceType, [vehicleId+date]',
  fuelEntries: 'id, vehicleId, date, odometer, isFillUp, [vehicleId+date], [vehicleId+isFillUp]',
  insurancePolicies: 'id, vehicleId, endDate, [vehicleId+endDate]',
  documents: 'id, vehicleId, category, date, linkedEntityType, linkedEntityId, [vehicleId+category]',
  reminders: 'id, vehicleId, status, odometerThreshold, dateThreshold, [vehicleId+status]',
  syncConflicts: 'id, userId, entityType, entityId, resolvedAt',
  syncQueue: '++autoId, entityType, entityId, operation, timestamp'
});
```

**Index Rationale:**
- Primary Keys: `id` (UUID) as primary key
- Foreign Keys: `userId`, `vehicleId` for joins
- Compound Indexes: `[userId+isActive]` for "get active vehicles for user" query
- Query Optimization: date, status fields for filtering
- Sync Queue: `++autoId` for FIFO processing order

### Coding Standards for Database Code
**[Source: architecture/12-coding-standards.md]**

**File Naming:**
- Schema definitions: `schema.ts`, `migrations.ts`
- Repository files: `{entity}-repository.ts` (kebab-case)
- Classes: `{Entity}Repository` (PascalCase)
- Database files: `cosmos-client.ts`, `dexie-db.ts`

**TypeScript Rules:**
- No `any` type; use explicit types from shared types
- All async functions must have try/catch
- All database errors logged with structured logging
- Parameterized queries only (Cosmos DB SQL with parameters)

**Validation:**
- Use Zod schemas from `@shared/schemas` for input validation
- Validate all user input before database operations
- Enforce constraints at data layer

**Repository Pattern:**
- All database access through repositories
- No direct SQL queries in business logic
- Repositories return domain objects (not raw Cosmos docs)
- Repositories handle error mapping

### Migration Strategy
**[Source: architecture/12-coding-standards.md and testing]**

**Migration Approach:**
- **File-based versioning:** `001-initial-schema.ts`, `002-add-field.ts`, etc.
- **Idempotent migrations:** Safe to run multiple times
- **Ordering:** Migrations run in numeric order
- **Execution:** Automatic on application startup (or manual via CLI)
- **Rollback:** Not automatic; require manual schema change + new migration

**Migration Testing:**

- Verify indexes are built
- Test schema change doesn't break existing code

### Database Query Patterns
**Using Compound Indexes for Performance:**

```typescript
// Bad: Full table scan without proper index
const events = await db.serviceEvents
  .where('vehicleId').equals(vehicleId)
  .toArray();

// Good: Uses compound index [vehicleId+date]
const recentEvents = await db.serviceEvents
  .where('[vehicleId+date]').between([vehicleId, startDate], [vehicleId, endDate])
  .toArray();
```

**Cosmos DB Queries:**
```typescript
// Use parameterized queries to prevent injection
const query = "SELECT * FROM c WHERE c.vehicleId = @vehicleId AND c.date >= @startDate";
const { resources } = await container.items
  .query({ query, parameters: [
    { name: '@vehicleId', value: vehicleId },
    { name: '@startDate', value: startDate }
  ]})
  .fetchAll();
```

### Error Handling for Database Operations
- All Cosmos DB calls in try/catch blocks
- Log errors with context (query, parameters, user)
- Return meaningful error messages to frontend
- Don't expose sensitive SQL/query details to client
- Use error code constants (COSMOS_CONN_FAILED, etc.)

### Sync Tracking Fields on All Entities
Every entity must include:
- `_version: number` - For conflict resolution (incremented on each update)
- `lastSyncedAt: DateTime | null` - Timestamp of last successful sync
- `createdAt: DateTime` - Record creation time (immutable)
- `updatedAt: DateTime` - Last modification time (updates on every change)

These fields enable the sync engine to detect conflicts and merge changes correctly.
