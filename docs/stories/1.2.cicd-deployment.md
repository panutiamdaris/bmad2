# Story 1.2: CI/CD Pipeline & Azure Deployment Setup

## Status
Approved

## Story
**As a** developer,  
**I want** automated build, test, and deployment pipeline using GitHub Actions with Azure infrastructure provisioned,  
**so that** code changes are automatically validated and deployed to staging/production environments without manual intervention.

## Acceptance Criteria
1. GitHub Actions workflow created for CI: lint, type-check, and build on every push/PR
2. Azure App Service provisioned for backend API (using free tier)
3. Azure Static Web Apps provisioned for frontend hosting (using free tier)
4. Azure Cosmos DB database provisioned with SQL API (using free tier)
5. Azure Blob Storage container created for file uploads (using free tier)
6. GitHub Actions workflow created for CD: deploy to staging on main branch merge, production on release tag
7. Environment variables configured in GitHub secrets for Azure connection strings and API keys
8. Deployment succeeds with "Hello World" endpoints verifying frontend and backend connectivity

### Infrastructure and Deployment Architecture
**[Source: architecture/10-infrastructure-and-deployment.md]**

**Cloud Provider:** Microsoft Azure (strategic choice)

**Key Azure Services for This Story:**
- **Azure App Service:** Backend hosting (serverless-like, cheaper than Function Apps for always-on)
- **Azure Static Web Apps:** Frontend hosting with built-in CDN, ideal for Next.js
- **Azure Cosmos DB:** NoSQL database with SQL API compatibility
- **Azure Blob Storage:** Document and image storage for vehicle photos, receipts
- **Azure Service Bus:** Message queue for async sync processing (configured later)
- **Azure API Management:** API gateway for rate limiting and monitoring (optional, but recommended)
- **Azure Application Insights:** Monitoring, logging, and performance tracking

**Deployment Strategy:**
- **Blue-Green with Slot Swaps:** Zero-downtime deployments using App Service deployment slots
  - Staging slot hosts new version
  - Smoke tests validate staging
  - Swap traffic to new slot
  - Quick rollback via slot swap (< 2 minutes)
- **Environments:**
  - Development (dev): Shared Cosmos DB (400 RU/s), consumption tier resources
  - Production (prod): Dedicated Cosmos DB (1000 RU/s), premium tier resources
- **Promotion Flow:** Developer Push → CI → Auto Deploy to Dev → Approval → Deploy to Prod → Smoke Tests → Traffic Switch

**Rollback Strategy:**
- Primary: Slot swap (fastest, ~2 minutes)
- Triggers: Failed smoke tests, error rate > 5%, manual command
- RTO (Recovery Time Objective): 2 minutes max

**Free Tier Considerations:**
- Azure free tier provides:
  - 1 App Service plan (Linux, shared)
  - 1 Static Web Apps instance (100 GB bandwidth/month)
  - 1 Cosmos DB account (400 RU/s, max 25GB)
  - 1 Storage account (5GB total)
- Limits: Monitor usage; may need to upgrade if exceeding free tier limits
- Cost: Zero while staying within free tier limits

### GitHub Actions Workflow Structure
**[Source: architecture/10-infrastructure-and-deployment.md]**

**Workflow Files Location:** `.github/workflows/`

**CI Workflow (ci.yml):**
- Triggers: push to all branches, pull requests
- Jobs: lint, type-check, build, test, smoke tests
- Failure: Blocks PR merge if any job fails
- Cache: Leverage actions/setup-node cache for faster installs

**CD Workflow for Staging (deploy-dev.yml):**
- Triggers: push to main branch
- Jobs: deploy backend, deploy frontend, smoke tests
- Automatic: Runs without approval
- Artifact: Reuses build artifacts from CI workflow

**CD Workflow for Production (deploy-prod.yml):**
- Triggers: GitHub release or tag
- Jobs: deploy to production slot, smoke tests, slot swap
- Manual Approval: Requires review before slot swap
- Rollback: Swap traffic back to previous slot if needed

### Azure Resource Provisioning Details

**Cosmos DB Configuration:**
- **Account:** SQL API (supports LINQ queries, required for migrations)
- **Database Name:** vehicle-tracker-db (or similar)
- **Consistency Level:** Session (read-your-writes, eventual consistency for other clients)
- **RU/s (Request Units):** 
  - Development: 400 RU/s (auto-scale, $0 in free tier)
  - Production: 1000 RU/s (escalated as load increases)
- **Regions:** Single region initially (East US 2 or West Europe)
- **Backup:** Automatic, point-in-time restore available

**Blob Storage Configuration:**
- **Account Type:** General-purpose v2 (supports all current storage types)
- **Replication:** Locally-redundant (LRS) for cost efficiency
- **Containers:**
  - documents: For vehicle photos, receipts, insurance documents
  - backups: For periodic exports (optional)
- **Access:** 
  - Private with SAS tokens (more secure)
  - Or: Public read for static assets (simpler, requires HTTPS)
- **Lifecycle Policies:** Delete old files after 90 days (configurable)

**App Service Configuration:**
- **OS:** Linux (cheaper than Windows)
- **Runtime Stack:** Node.js 20.11.0 LTS
- **Tier:** Free (B1 shared, 1 core, 1.75 GB RAM)
- **Deployment Slots:**
  - Production (live traffic)
  - Staging (for testing before traffic switch)
- **App Settings:**
  ```
  AZURE_COSMOS_CONNECTION_STRING=<from Secrets>
  AZURE_BLOB_STORAGE_CONNECTION_STRING=<from Secrets>
  NODE_ENV=production
  API_BASE_URL=https://<app-service-url>
  ```

**Static Web Apps Configuration:**
- **Tier:** Free (provides 100 GB bandwidth/month)
- **Build Details:**
  - Build preset: Next.js 14
  - App location: packages/web
  - Output location: .next (or out for static export)
- **Deployment Slots:**
  - Production (main branch)
  - Staging (preview for PRs)
- **App Settings:**
  ```
  NEXT_PUBLIC_API_BASE_URL=https://<app-service-url>
  ```

### Health Check Endpoint Implementation
The health check endpoint is critical for detecting deployment issues:

**Backend Health Check: `GET /health`**
```typescript
// Response on success (200 OK)
{
  "status": "healthy",
  "timestamp": "2026-01-09T15:30:00.000Z",
  "dependencies": {
    "cosmos": "healthy",
    "blob_storage": "healthy"
  }
}

// Response on failure (503 Service Unavailable)
{
  "status": "unhealthy",
  "timestamp": "2026-01-09T15:30:00.000Z",
  "dependencies": {
    "cosmos": "error: connection timeout",
    "blob_storage": "healthy"
  },
  "message": "Cosmos DB unavailable"
}
```

### Environment-Specific Configuration
Different environments require different settings:

**Development Environment:**
- Cosmos DB: Shared, 400 RU/s
- App Service: Free tier
- Static Web Apps: Free tier
- Debugging: Enabled, verbose logging

**Production Environment:**
- Cosmos DB: Dedicated, 1000 RU/s
- App Service: Standard tier (if traffic requires)
- Static Web Apps: Free tier with CDN
- Debugging: Disabled, structured logging only
- Monitoring: Application Insights enabled
- Backup: Enabled, daily snapshots

### Deployment Rollback Procedures

**Automatic Rollback Triggers:**
1. Smoke tests fail on staging
2. Error rate > 5% in first 15 minutes
3. Health check endpoint returns 503

**Manual Rollback:**
1. Swap slots back (App Service slot swap)
2. Redeploy previous Static Web Apps version
3. Investigate root cause

**Rollback Time:** < 2 minutes target

### Testing Requirements for This Story

**Smoke Test Scenarios:**
1. **Frontend Hello World Test:**
   - Navigate to frontend URL
   - Verify page title loads
   - Verify "Hello World" text displays
   - Verify no console errors

2. **Backend Hello World Test:**
   - Make GET request to /api/hello
   - Verify 200 status code
   - Verify response contains expected message

3. **Health Check Test:**
   - Make GET request to /api/health
   - Verify 200 status code
   - Verify all dependencies are healthy
   - Verify timestamp is recent

4. **Cosmos DB Connectivity Test (via health check):**
   - Health check includes Cosmos DB status
   - If status is "healthy", test passes
   - If status is "error", deployment failed

5. **Cross-Domain Request Test:**
   - Frontend makes fetch request to backend API
   - No CORS errors in browser console
   - Request succeeds with 200 status

6. **Environment Configuration Test:**
   - All required env vars are set in App Service
   - All secrets are configured in GitHub Secrets
   - No missing configuration errors in logs
