# Story 1.5: Frontend Authentication Flow & Protected Routes

## Status
Draft

## Story
**As a** vehicle owner,  
**I want** a registration and login interface that redirects me to the app after authentication,  
**so that** I can access my account and begin tracking vehicles without friction.

## Acceptance Criteria
1. Login page component with email and password fields, "Log In" button, and "Register" link
2. Registration page component with email, password, confirm password fields, and "Create Account" button
3. Form validation displays inline errors for invalid email format, password mismatch, or weak passwords
4. Successful login stores JWT in memory and refresh token in cookie, redirects to dashboard
5. Successful registration automatically logs user in and redirects to dashboard
6. Protected route wrapper redirects unauthenticated users to login page
7. Axios interceptor automatically includes JWT in Authorization header for API requests
8. Axios interceptor handles 401 responses by attempting token refresh, retrying original request, or redirecting to login
9. Logout button clears tokens and redirects to login page

### Authentication Flow Diagram
**[Source: architecture/07-core-workflows.md]**

**User Registration and First-Time Setup:**
```
User clicks "Sign Up"
  ↓
Registration form validates input locally
  ↓
POST /api/auth/register (email, password)
  ↓
Backend validates, hashes password, creates user
  ↓
Response: { user, accessToken }
  ↓
Frontend stores accessToken in Zustand
  ↓
Redirect to /dashboard
```

**User Login:**
```
User enters email/password
  ↓
Login form validates input
  ↓
POST /api/auth/login (email, password)
  ↓
Backend validates credentials
  ↓
Response: { user, accessToken } + Set-Cookie: refreshToken
  ↓
Frontend stores accessToken in Zustand, refreshToken in httpOnly cookie
  ↓
Redirect to /dashboard
```

**Token Refresh (Automatic on 401):**
```
API request returns 401
  ↓
Axios interceptor catches 401
  ↓
POST /api/auth/refresh (includes refreshToken cookie)
  ↓
Backend validates refresh token, issues new accessToken
  ↓
Axios interceptor retries original request with new token
  ↓
If successful, return response to caller
  ↓
If failed, clear auth state, redirect to login
```

**Logout:**
```
User clicks "Logout" button
  ↓
Call logout API (optional, for cleanup)
  ↓
Clear accessToken from Zustand
  ↓
Clear user from Zustand
  ↓
Redirect to /login
```

### Token Storage Strategy
**[Source: architecture/14-security.md]**

**Access Token:**
- Stored in Zustand store (memory only)
- Expires in 15 minutes
- Included in Authorization header for API requests
- Cleared on logout

**Refresh Token:**
- Stored in httpOnly secure cookie (set by backend)
- Expires in 7 days
- Not accessible to JavaScript (prevents XSS theft)
- Automatically sent with requests via cookie
- Used to request new access token when needed

**Why This Strategy:**
- Access token in memory: Can't be stolen by XSS attacks targeting localStorage
- Refresh token in httpOnly cookie: Can't be accessed by JavaScript, but automatically sent
- Combines security (httpOnly) with UX (seamless refresh)

### Protected Routes Implementation
**[Source: architecture/05-components.md and 07-core-workflows.md]**

**Protected Route Pattern:**
```tsx
// In dashboard layout
export default function DashboardLayout({ children }) {
  return (
    <ProtectedRoute>
      {/* Header with logout button */}
      <Header />
      {/* Page content */}
      {children}
    </ProtectedRoute>
  );
}
```

**What ProtectedRoute Does:**
1. Check if accessToken exists in Zustand
2. If yes, render children
3. If no, redirect to /login
4. While checking, show loading spinner
5. Handle token expiry by attempting refresh

### Coding Standards for Frontend Auth
**[Source: architecture/12-coding-standards.md]**

**File Naming:**
- Components: PascalCase in kebab-case files (ProtectedRoute in protected-route.tsx)
- Pages: lowercase (page.tsx)
- Utilities: kebab-case (auth-service.ts, form-validation.ts)
- Stores: kebab-case ending with -store (auth-store.ts)

**React Component Rules:**
- Functional components only
- Explicitly typed props with interfaces
- Custom hooks for reusable logic (useAuth, useForm)
- useCallback for callback props

**TypeScript Rules:**
- No `any` type
- Explicit return types on functions
- Interface for object shapes
- Discriminated unions for different states (loading, error, success)

**Error Handling:**
- Try/catch blocks for async operations
- User-friendly error messages
- Log errors with context (not passwords/tokens)
- Never expose stack traces to users
