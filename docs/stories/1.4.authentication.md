# Story 1.4: User Authentication & Registration

## Status
Draft

## Story
**As a** vehicle owner,  
**I want** to register an account with email/password and log in securely,  
**so that** my vehicle data is private and accessible only to me across devices.

## Acceptance Criteria
1. POST /api/auth/register endpoint accepts email and password, creates user with bcrypt-hashed password
2. POST /api/auth/login endpoint validates credentials and returns JWT access token and refresh token
3. JWT access tokens expire after 15 minutes; refresh tokens stored in httpOnly secure cookies
4. POST /api/auth/refresh endpoint accepts refresh token and issues new access token
5. POST /api/auth/logout endpoint invalidates refresh token
6. Email validation enforces valid format; password requires minimum 8 characters
7. Registration prevents duplicate emails with clear error message
8. Authentication middleware validates JWT on protected routes and returns 401 for invalid/missing tokens
9. Unit tests cover registration, login, token refresh, and authentication middleware

### Authentication Architecture Overview
**[Source: architecture/14-security.md]**

**Authentication Strategy:**
- JWT tokens for stateless authentication
- Access tokens: 1 hour expiry (PRD says 15 minutes, security doc says 1 hour - use 15 minutes from PRD for MVP)
- Refresh tokens: 7 days expiry, stored in httpOnly cookies
- No token blacklist needed (stateless JWT)
- Each protected route validates JWT before processing

**Security Requirements:**
- Input validation with Zod schemas
- Password hashing with bcrypt (salt rounds = 10)
- Email validation (RFC 5322 compliant)
- Password strength requirements: minimum 8 characters
- HTTPS enforced in production
- CORS restricted to trusted origins
- Rate limiting on auth endpoints (Story 1.2 configured this)

**Secret Management:**
- Dev: Secrets stored in .env file (gitignored)
- Production: Secrets in Azure Key Vault with managed identities
- Never log passwords or tokens
- Rotate secrets quarterly
- All secrets in environment variables, not hardcoded

### Technology Stack for Authentication
**[Source: architecture/03-tech-stack.md and architecture/14-security.md]**

**Required Packages:**
- **bcryptjs:** 2.4.3 (password hashing - use bcryptjs for Node.js compatibility)
- **jsonwebtoken:** 9.1.0 (JWT token generation and verification)
- **zod:** 3.22.4 (request validation)
- **node-jose:** (optional, for key management)

**JWT Configuration:**
- Algorithm: HS256 (HMAC with SHA-256)
- Issuer: Optional, can use app name
- Subject: userId
- Audience: Optional, can specify web app
- Access token expiry: 15 minutes (900 seconds)
- Refresh token expiry: 7 days (604800 seconds)

**TypeScript Version:** 5.3.3 (strict mode required)

### Cosmos DB User Document Structure
**[Source: docs/stories/1.3.database-schema.md]**

**User Table Schema in Cosmos DB:**
```typescript
interface User {
  id: string;                    // UUID from crypto.randomUUID()
  email: string;                 // Lowercase, unique index
  password_hash: string;         // bcrypt hash, never returned in API
  displayName: string;           // User's display name (can be empty initially)
  createdAt: string;             // ISO 8601 timestamp
  updatedAt: string;             // ISO 8601 timestamp
  preferences: {
    distanceUnit: 'miles' | 'kilometers';
    fuelVolumeUnit: 'gallons' | 'liters';
    currency: string;            // e.g., 'USD', 'EUR'
    locale: string;              // e.g., 'en-US'
  };
  syncEnabled: boolean;          // Default: true
  lastSyncAt: string | null;     // ISO 8601 timestamp or null
}
```

**Partition Key:** `/userId` (but for users container, partition by userId would be self - special handling)

**Indexes:**
- `id` (primary key, unique)
- `email` (unique index for duplicate prevention)
- `createdAt`, `lastSyncAt` (for queries)

### Email Validation
**[Source: architecture/14-security.md]**

Email validation must:
- Check format validity (RFC 5322)
- Not need to verify deliverability (no email sending in MVP)
- Reject obviously invalid formats
- Allow common special characters (+, -, _)

Use Zod email validation or simple regex:
```typescript
const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
```

### Password Requirements
**[Source: architecture/14-security.md]**

Password must:
- Be minimum 8 characters
- Contain at least one uppercase letter (optional for MVP, but good practice)
- Contain at least one lowercase letter (optional for MVP)
- Contain at least one digit (optional for MVP)

For MVP, minimum requirement: 8 characters. Complexity rules can be added later.

### JWT Claims Structure
**[Source: architecture/14-security.md]**

Access Token Payload:
```json
{
  "userId": "uuid",
  "iat": 1234567890,
  "exp": 1234568790,
  "type": "access"
}
```

Refresh Token Payload:
```json
{
  "userId": "uuid",
  "iat": 1234567890,
  "exp": 1234654190,
  "type": "refresh"
}
```

Always include `type` field to prevent token confusion.

### Coding Standards for Auth Code
**[Source: architecture/12-coding-standards.md]**

**File Naming:**
- Auth functions: `{action}.ts` (kebab-case) - e.g., `register.ts`, `login.ts`
- Auth utilities: `{purpose}-utils.ts` - e.g., `password-utils.ts`, `jwt-utils.ts`
- Middleware: `{purpose}-middleware.ts`
- Test files: `{filename}.test.ts` colocated with source

**TypeScript Rules:**
- No `any` type usage
- Explicit return types on all public functions
- Use `interface` for object shapes
- No direct `Error` throws; use custom error classes
- All async functions wrapped in try/catch

**Constants:**
- Use SCREAMING_SNAKE_CASE: `JWT_EXPIRY_MINUTES`, `BCRYPT_SALT_ROUNDS`
- Define in separate config files, not inline

**Error Handling:**
- Never log passwords or tokens
- Always include request ID in error logs for debugging
- Use error code constants (INVALID_CREDS, EMAIL_EXISTS, etc.)
- Return user-friendly error messages in API responses

**Security Rules:**
- Never store passwords in code
- All secrets from environment variables
- Validate input before processing
- Hash passwords before storing
- Use httpOnly cookies for refresh tokens
- Validate CORS origin
- Rate limiting on auth endpoints (configured in Story 1.2)
